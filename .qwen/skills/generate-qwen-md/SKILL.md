# Generate QWEN.md — Анализ проекта и генерация контекстного файла

## Когда использовать

Когда пользователь просит **проанализировать текущий проект** и создать/обновить `QWEN.md`, или когда в начале работы с новым проектом нужно понять его структуру и зафиксировать контекст.

## Процесс

### 1. Первичная разведка

- **Прочитать `README.md`** (или `README.txt`) — это самый быстрый источник общей картины
- **Посмотреть `.gitignore`** — часто показывает, какие технологии/фреймворки используются
- **Проверить конфигурационные файлы** верхнего уровня: `package.json`, `requirements.txt`, `go.mod`, `Cargo.toml`, `composer.json`, `pyproject.toml`, `Makefile`, `Dockerfile`

### 2. Глубокое погружение (до 10 файлов)

Выбирать файлы для чтения итеративно, в порядке приоритета:

1. **Главные конфиги** (конфигурация приложения, CI/CD, линтеры)
2. **Основные исходные файлы** (точки входа, ключевые модули/классы)
3. **Скрипты сборки/деплоя/запуска**
4. **Вспомогательные файлы** (тесты, утилиты)

После каждого прочитанного файла уточнять понимание и решать, какие файлы читать дальше.

### 3. Идентификация типа проекта

**Кодовый проект** (признаки):
- Наличие `package.json`, `requirements.txt`, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle`
- Наличие `src/`, `lib/`, `app/` директорий
- Наличие тестов (`tests/`, `spec/`, `__tests__/`)
- Наличие систем сборки (`Makefile`, `Dockerfile`, `webpack.config.js`)

**Некодовый проект** (признаки):
- Только документы, заметки, PDF, изображения
- Отсутствие исполняемых скриптов и конфигурации сборки
- Наличие `*.md`, `*.txt`, `*.pdf`, `*.drawio` и т.п.

### 4. Структура генерируемого QWEN.md

#### Для кодового проекта:

```markdown
# <Project Name> — QWEN Context

## Project Overview

- Назначение проекта (одним-двумя абзацами)
- Основной workflow / бизнес-логика
- Технологии: язык, фреймворк, база данных, инфраструктура

## Architecture

- Структура директорий (дерево)
- Описание каждого значимого модуля/компонента
- Связи между модулями (кто кого вызывает, потоки данных)
- Внешние зависимости (API, библиотеки)

## Key Conventions

- Code style (именование, типизация, форматирование)
- Error handling (логирование, исключения, коды возврата)
- Архитектурные паттерны (если применимо)
- Особенности конфигурации (переменные окружения, environment)

## Building and Running

- Установка зависимостей
- Команды сборки (dev, production)
- Команды запуска (локально, тесты, линтер)
- CI/CD pipeline (если есть)

## Testing

- Фреймворк для тестов
- Структура тестов
- Особенности моков/фикстур

## Deployment

- Как деплоится проект
- Ключевые команды/скрипты

## Security

- Чувствительные данные (токены, ключи, пароли)
- Файлы, которые не должны попасть в репозиторий
```

#### Для некодового проекта:

```markdown
# <Directory Name> — QWEN Context

## Directory Overview

- Назначение директории
- Тип информации (документация, исследования, заметки)

## Key Files

- Таблица с описанием каждого значимого файла:
  | File | Description |
  |---|---|

## Usage

- Как использовать содержимое директории
- Связанные ресурсы/тулы
```

### 5. Финальный шаг

Записать результат в `QWEN.md` в корне проекта. Если файл уже существует — прочитать его перед перезаписью (требование инструмента `write_file`).

## Важные замечания

- Не дублировать информацию из `README.md` — структурировать её заново под формат QWEN-контекста
- Названия модулей, команд и путей давать в оригинале (не переводить)
- Для CLI-команд указывать конкретные примеры из проекта, не шаблонные
- Если проект не содержит тестов — явно указать это и дать рекомендации по их добавлению
